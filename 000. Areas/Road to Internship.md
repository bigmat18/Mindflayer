##### Tell me about a time when you worked on a project with limited direction. What did you do?
**ANSWER 1**
**Situations**: During one of my master degree course I was asked to implemented an efficiente algorithm for mesh processing using gpgpu techniques, but there was little clarity on what the end result should be.
**Task**: My responsibility was to identify the key issues on the naive solution proposed and find a way to improve the efficiency to reduce the time and memory used by it.
**Action**: I clarified the pain points with profiling tools and I found that many of the time was spent on data reading from global memory. I then engineered a new structure of algorithms that allow to use in a more efficiency way the data to reduce the memory access storing information in shared memory. From this I taking the initiative to redesigned how the algorithm process information and how store it.
**Result**: As a result, the time to process the same amount of data decrease up to 30%, which significantly improved how it can be used in real situations
**Learning**: From this experience, I learned the importance of asking the right questions, taking initiative and using technical expertise to bring clarity where direction is limited. These are skills I would bring to projects here at Databricks.

**ANSWER 2**
**Situations:** During my experience at a startup building a platform for financial education and investments, I was asked with designing a cloud architecture to lower costs compared to the existing solution. 
**Task:** My responsibility was to identify the services that contributed most to spending and define alternatives that would reduce costs while preserving maximum flexibility for future scalability, but there was little clarity on what I should did in practice.
**Action**: First, I clarified the pain points using profiling and cost-analysis tools, finding that a significant portion of costs came from database services. I also discovered that, with the current configuration, the cost of backend machines would quickly become unsustainable with scaling. I then redesigned the cloud architecture by simplifying it and adopting lower-cost services. After a series of tests, I selected more appropriate instance sizes for the backend and configured autoscaling with a load balancer to handle peak traffic. I taking the initiative and I also optimized database settings and provisioning policies to align with real usage patterns and improve the security.
**Result**: The outcome was an infrastructure that remained reliable and efficient while reducing costs by up to 50% and improving elastic scalability
**Learning**: From this experience, I learned the importance of asking the right questions, taking initiative, and using technical expertise to bring clarity when direction is limited. These are skills I would bring to projects at Databricks.

##### Tell me about a time when you tried something risky and failed?
**Situation:** During my Bachelor's degree, I followed an important course on low-level programming and multi-threading in C called Laboratory II.
**Task:** The final exam required us to develop a multi-threaded application from scratch in C. The project required to handle concurrent file I/O, implementing synchronization patterns like producer-consumer, and handling inter-process communication via sockets.
**Action:** Even with a short deadline, I decided to take a calculated risk. I tried to build a much bigger and more complex system, something that can be modular and reusable. I spent a lot of time in creating custom data structures, a generic multi-threaded file I/O system, and a robust socket protocol designed to handle interruptions. My goal was to create something truly robust and well-engineered, not just to pass the exam.
**Result:** While my ambition was high, the system's complexity become too complex for me to handle in time, especially considering my experience with C at the time. I was too focused on my big plan and didn't realize how much time I would need for debugging low-level concurrency issues. In the end, I delivered a project that had a good idea behind it, but it didn't work well and had many serious bugs. It was a failure.
**Learning**: I learned to prioritise delivering a working, have a product before adding layers of complexity. Now, when I start a new project, I always focus on the core requirements first to make sure I deliver on time, and only then I add more advanced, modular features. This experience taught me how to find the right balance between big ambitions and realistic deadlines, a skill I consider essential and I want to use in Databricks.

##### How do you handle changes or unexpected obstacles during a project? Can you provide an example of a challenging project you successfully completed?
**Situation**: For my bachelor's thesis, I developed a system to render 3D lines and polylines with variable thickness and visual effects. The system was designed to be general-purpose and multi-platform, aiming to provide high-quality rendering with good performance for uses like data visualization. To achieve this, I created five different implementations, each using a unique technique to process the geometry and pass data to the GPU. The final step was to run a comprehensive benchmark suite to analyze my results and compare the performance of each implementation against a baseline.
**Task**: I was just three days away from the final submission deadline. My main task was to finalize the performance analysis and write my conclusions. However, as I was running the final validation tests, I discovered a critical issue: one of my implementations had a memory leak on the GPU.
Specifically, in the benchmarks where I updated the line buffer every few frames, the old data was accumulating in the GPU's memory instead of being deallocated. This eventually caused the program to crash when the GPU memory ran out, which made the benchmark results completely wrong.
**Action:** The first thing I did was stay calm and use a systematic approach to find the problem.
I started by debugging the code, carefully checking every point where a new memory allocation was made. By doing this, I found the exact line in my code that was allocating the memory that was accumulating.
With this knowledge, I tried to understand why the memory wasn't being deallocated, even though I was calling the free function. I decided to study the rendering library's code (bgfx) in debug mode to see how it handled deallocations, especially since it works asynchronously. I used my other, working implementations as a reference point to see the correct process.
By comparing the working cases with the failing one, I discovered the root cause: I was missing a specific flag when I allocated my buffer. This missing flag caused the library to skip the deallocation step for that buffer, leaving it in memory. Once I added the correct flag, the bug was fixed.
**Result**: In the end, I was able to generate accurate, validated results, complete my analysis, and submit my thesis on time.
**Learning**: More importantly, this experience taught me two things: first, the absolute importance of rigorous, end-to-end testing. And second, how to stay methodical and focused when facing unexpected, high-stakes obstacles. It reinforced that even under extreme pressure, a calm and structured approach to problem-solving is the fastest way to a solution.
